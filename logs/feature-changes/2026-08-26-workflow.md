## Summary

Eleven chapters said what Sufyan built, where he worked and what he won, and none said **how** he
works. The owner supplied `reference/workflow-reference.mp4` (16 s, an Indonesian portfolio) and
asked for a Workflow chapter under Achievements with that flow, extending the reference's three
steps (Diskusi / Perencanaan / Pengembangan) with **Quality Testing** and **Maintenance**.

Built as a pinned rail: five step nodes travel leftward along one dashed track, whichever is at
horizontal centre is the active step, and its title + description resolve out of a blur below it.
Opens on a centred intro card (eyebrow + statement + lede) that blurs away as the rail fades up —
the reference's own entrance.

**This is an owner-ask chapter, not a PRD transcription** — see "Content provenance" below.

## Notable decisions

- **Nothing translates as a group — the inversion that makes this cheap.** The reference reads as
  "a rail sliding left", but building it literally puts five `--text-chapter` titles inside one
  transformed track at ~190 px spacing: they overlap, and each needs a counter-translation write
  to stay legible. Instead every step is an `absolute inset-0` overlay of the whole stage; only
  its `.wf-travel` cluster (disc + bubble) takes the per-frame `x`, and `.wf-copy` sits at a fixed
  centred position and merely crossfades. Same picture, one list, no counter-translation.
- **Articles' measurement step is deleted.** Articles measures `track.scrollWidth − innerWidth`
  because its travel depends on how many cards exist. Here travel is *choreography* (n × `gap`),
  so every position is arithmetic — no track element, no `offsetLeft` metrics array, no
  `ResizeObserver`. The only per-refresh read is `innerWidth`.
- **The tail is a real hold, not Articles' slow-down.** `TRAVEL_FRAC` excludes `tailVh` from the
  playhead map, so the playhead reaches step 5 and then genuinely sits there.
- **Smoothstep, not linear, for activeness.** Linear read as mush through the crossfade;
  `smoothstep(0.5) === 0.5`, so two neighbours' opacities sum to 1 at mid-transit and the fold
  never dips dark between steps.
- **The disc is `bg-paper`, not `bg-accent`.** A 128 px ember disc is a wash, not a scalpel. Ember
  appears exactly twice in the chapter: the eyebrow index, and one 4 px connector dot between disc
  and bubble, visible only while a step is centred. The light disc also keeps faith with the
  site's existing invert vocabulary (Achievements' fill bar, Contact's sheet).
- **The progress track needs no animation.** The active node is always at horizontal centre, so
  the traversed/ahead boundary is permanently at 50 % — two static half-width elements with
  different `repeating-linear-gradient` cycles, zero per-frame writes. Rejected `scaleX` (stretches
  the dash *pattern*) and `clip-path` (a per-frame string for a boundary that never moves). The
  phase discontinuity at the seam sits under the disc that is always parked exactly there.
- **Plain `opacity` everywhere, never `autoAlpha`.** `autoAlpha` resolves to `visibility: hidden`,
  which deletes the node from the accessibility tree — and four of five process steps plus the
  chapter's own h2 spend most of this pin at opacity 0. Nothing here is interactive, so opacity
  alone costs nothing. This diverges from Articles/Gallery deliberately.
- **`grayscale()` deliberately absent.** The reference greys because it is a light site with
  coloured icons; our rail is already neutral, so it would be a per-frame no-op with a real cost.
  Opacity toward `bg-ink` *is* the greying here.
- **Static fallback is a vertical `<ol>`, and `staticMode = prefersReducedMotion` only.** Articles'
  `fitsInView` guard does not port — travel is `lastIndex × gap`, always positive, so there is no
  degenerate case to detect; and `gap.min` 150 keeps both neighbours on screen at 390 px, so there
  is no mobile branch either. One code path.
- **Settled state is the markup default** (Achievements precedent): all five steps render filled
  and legible, and only the motion branch idles them — which is what makes the reduced-motion path
  a readable list for free.
- **Icon is a string key, not a component.** A `LucideIcon` in `portfolio.ts` would drag React and
  lucide into the content contract. The key → component map is six lines in the section, and a bad
  key fails compilation (`tech-icons.ts` is the same shape).

### Geometry calibrated against the reference, not eyeballed

Frame-measured from `hi_3.6` (crop `3600×1400+0+500`, scaled to 1400 — i.e. ≈0.926 of the
reference's CSS width, so the crop reads near-1:1 against our 1440 viewport):

| | reference (CSS) | first build | shipped |
| --- | --- | --- | --- |
| disc diameter | ~127 px | 112 (`size-28`) | **128 (`size-32`)** |
| title size | ~84 px | 96 (`--text-chapter`) | 96 — token, kept |
| disc-bottom → title-top | ~57 px | 144 (`+9rem`) | **64 (`+8rem`)** |
| track height | 44.5 % | 45 % | 45 % |

Title stays on `--text-chapter`: there is no 84 px token, and inventing one to shave 12 px would
fail the tokens-only rule for no visible gain. The disc grew instead, which fixes the same ratio.
`liftPx` and `discScaleFrom` are **derived from** those class sizes (`112 = 64 + 24 + 24`;
`0.375 = 48/128`) and are annotated as coupled — change a size class and both must move.

### Harness note (cost me time, worth recording)

chrome-devtools MCP reported `rafPerSec: 2` at every scroll position on the page and
`Page.captureScreenshot` timed out repeatedly — which looks exactly like a catastrophic perf
regression. It is not. The tell: a 5M-iteration `Math.sqrt` loop finished in **7 ms** and
`setTimeout` ran **208×/sec** while rAF ran 2×/sec. Main thread idle + timers fine + vsync starved
= the Chrome window is occluded or minimised, so the compositor produces no frames (the same
window state that made `resize_page` error with "Restore window to normal state"). All numbers
above were re-taken with the documented headless puppeteer-core fallback, which has no such state.
**If rAF reads ~2 fps uniformly across the whole page including a static section, suspect the
window, not the code.**

# 10 Workflow — intro-reveal desync fix + enriched step copy

- **Date:** 2026-08-26 (same day, follow-up pass)
- **Author:** main
- **Type:** fix + feat
- **Chapter/Area:** 10 Workflow

## The bug (owner report + screenshot)

The rail faded in over a statement that was still less than half revealed — dashed track, node 01
and the "Discovery" title all visible *through* the words "the same five steps".

**Root cause, and it is a general GSAP trap worth remembering.** The intro timeline used Articles'
per-word `stagger: 0.09` with `duration: 0.5`. `WORKFLOW_STATEMENT` is **19 words**, so the cascade
actually ran `0.5 + 0.09 × 18 = 2.12 s`. GSAP sizes a timeline to its longest child, so `introTl`
became 2.12 s long — but the intro-out / rail-in tweens were placed at *absolute* positions 0.55
and 1.0, written on the assumption of a 1.0 s timeline. `introTl.progress()` therefore mapped the
handoff to **26 %–47 %** of the cascade. At the moment the rail was fully in, the words were
`1.0 / 2.12 = 47 %` revealed — which is exactly what the screenshot shows.

**The fix is `stagger: { amount }`, not a bigger number.** `amount` spreads the word *starts* across
a fixed window regardless of how many words there are, so the cascade length no longer depends on
the copy. The timeline is now four explicit, bounded segments totalling exactly 1.0:

| position | what |
| --- | --- |
| 0 → 0.60 | word cascade (`wordSpread 0.38` + `wordDuration 0.22`), then `filter: none` |
| 0.60 → 0.68 | read beat — statement fully legible, nothing moving |
| 0.68 → 1.00 | intro blurs out / rail fades in |

`pin.headVh` 0.6 → **0.8**, because the cascade now finishes at 60 % of the head beat and the
remaining 40 % is the read beat; at 0.6 that was under a quarter-viewport of scroll. Pin length
3.95 vh → 4.15 vh.

Two guards so this cannot regress silently:
- A **dev-only `console.warn`** if `introTl.duration() !== 1`. The failure mode was invisible —
  nothing errored, the numbers just meant something different than they read.
- The tunable doc comment states the invariant (`wordSpread + wordDuration <= handoffAt` and
  `handoffAt + handoffDuration === 1`) and records why, so re-voicing the statement is safe.

**Carry to other chapters:** `ArticlesSection` uses the same per-word `stagger` pattern. It gets
away with it *today* because its `headingTl` is a single-tween timeline, so normalising over the
longer duration is harmless. The moment anyone adds a second positioned tween to it, it acquires
this exact bug.

(12 px, needs 4.5:1). They are announced `<li>`s, not ornament, so this was a real AA failure and
not a style choice. Now `text-muted` (**7.04:1**). They still read quieter than the description
because they are a third of its size, not because they are dimmer.
