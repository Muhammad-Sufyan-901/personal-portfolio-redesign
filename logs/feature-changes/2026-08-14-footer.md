## Notable decisions

- **Section lives in `features/home/sections/`, not `components/shared/Footer.tsx`** as PLAN specced. It consumes `profile` / `socialLinks` from `features/home/data/*`, and a `components/shared/` module reaching into a feature inverts the direction Golden Rule 1 protects. PLAN's other half ("rendered by HomePage after Contact") is honoured.
- **Ported the three.js engine rather than pre-baking the ASCII grid** — owner's explicit pick at the plan gate. Cost is a second WebGL context; mitigated below.
- **One `<pre>`, spotlight via `background-clip: text` + a radial gradient**, not two stacked layers with a mask (halves the per-frame relayout) and not per-cell spans (~10k nodes). The gradient's last stop extends forever, so its outer colour doubles as the field's resting ember.
- **`contain: strict` + explicit px size on the `<pre>`** — each rebuild relayouts a ~7.5k-char block; containment keeps that inside the element instead of dirtying the footer's layout tree.
- **15 fps, not 60.** The field is noise; nobody can see the difference and it quarters the cost.
- **`--font-ascii` is a new token, not a hard-coded stack.** `--font-mono` renders Inter by design (2026-07-20), and Inter is proportional — ASCII columns jitter without a fixed advance. System stack, so no webfont cost.
- **Lazy boundary at the section** (`React.lazy`, ManifestoSection's pattern). Eager-importing three pulled it into the entry chunk: 521 kB → 1,025 kB. With the boundary the entry chunk is back to 521.75 kB and three stays in its own lazy `three.module` chunk (734.00 kB / 189.93 kB gzip), shared with the already-lazy `ManifestoCanvas`. `AsciiHands` itself is 4.74 kB.
- **Hands live in normal flow (`flex-1`), not absolute percentage insets.** The first build used `top-[22%] bottom-[26%]`, which collided with the wrapped link columns at 390 px. `flex-1` is correct at every viewport; `-mx-page-x` keeps the full bleed.
- **Dropped from PLAN v3.1 §3:** name `Marquee`, back-to-top `MagneticButton`, ember "ornament converge". The video has a static name and no back-to-top, and the ASCII hands *are* the ornament.

### Constraint worth remembering

`Preloader.tsx:122` polls `.hero-name .hero-word` and requires **exactly two** matches document-wide for its FLIP morph. A giant name anywhere else must use different class names — hence `.footer-name` / `.footer-word`. Verified 2 hero words at runtime after the footer landed.

## Audit findings fixed in this commit

- **F1 (Major) — the skip link scrolled but never moved focus**, so it bypassed nothing. Root cause was in the shared hash branch of `components/common/Link.tsx`, not the footer: `preventDefault()` kills the browser's fragment-navigation focus reset and `pushState` never sets one. Fixed once at the shared primitive (`tabindex="-1"` + `focus({ preventScroll: true })` on the target), which repairs every SiteMenu and footer anchor too. Verified: `document.activeElement` is now `SECTION#hero`.
- **F2 (Major) — skip link failed AA.** `text-paper-bright` on `bg-accent` measured **3.68:1** at 13px (`--text-eyebrow` is too small to count as large text). Now `text-ink` → **4.72:1**, verified at runtime. Ring is `focus:outline-ink` because the global ember `:focus-visible` was ember-on-ember. **Nothing lighter than ~#B0B0B0 passes on ember** — remember before using ember as a text background again.
- **F3 (Minor) — the pointer spotlight wasn't gated by the IO that gates the draw loop.** A mouse move at the hero still forced a layout read plus two tweens per frame against an 11,704-char `<pre>`. One-line `if (!onScreen) return;`. Verified: offscreen, 12 pointer moves now change `--ascii-x` not at all.
- **F4 (Minor) — the z-60 HUD label parked on the footer name** (18 px overlap at 1440, `mix-blend-difference` inverting it against the paper glyph). The footer isn't a `navLinks` chapter, so past Contact the label has nothing to name: the HUD now **retires** at the footer (`ScrollProgressHUD` reveal trigger ends 0.35 vh before the footer top instead of `HUD_END`). Verified opacity 1 → 0.
- **F5 (Info)** — corrected the chunk figure in this log; `three.module` is 734.00 kB, not 286 kB.

Not changed: the two `mailto:` stops in the footer (address line + "Gmail" label) are distinct accessible names to one destination — legitimate, and matching the reference's shape.

## Art landed same day — image prep + calibration

Owner supplied `hands.jpg` (the *Creation of Adam* composition, exactly right). Two problems and the fixes:

1. **It was a PNG with no alpha** — the editor's transparency checkerboard had been flattened into real grey pixels (`#404140`), which would have rasterised as a solid field of glyphs behind the hands. The checker is neutral (`max−min ≤ 2`) and skin is not (`≈45–65`), so it keys cleanly on **saturation**. Recipe, re-runnable if the art changes:
   ```
   MX="max(max(r(X,Y),g(X,Y)),b(X,Y))"; MN="min(min(r(X,Y),g(X,Y)),b(X,Y))"
   M="clip((($MX)-($MN)-5)/12,0,1)"
   ffmpeg -i hands.jpg -vf "format=rgba,geq=r='r(X,Y)*($M)':g='g(X,Y)*($M)':b='b(X,Y)*($M)':a='255*($M)'" hands.png
   ```
   RGB is multiplied by the mask too, so feathered edges go dark instead of bright.
2. **~30% of its height was empty padding** (substantive rows 111–601), which shrank the hands inside the band. Cropped to `1456×502` (2.90:1). Source kept at `reference/hands-source.png` — moved out of `public/` because 1.4 MB of unused art was being copied into `dist/`.

Calibrated against the reference by measurement, not eye:

- **Grid pitch.** Autocorrelating a dense strip of the reference field gives a **20 px pitch in its 3600 px frame → 180 columns**. Ours measures 183 at 1440. `TARGET_COLS` is now the knob and the cell is solved from it.
- **Glyph brightness.** Over a matched-CSS-scale patch the reference runs meanR 12.8 / p95 34 / lit 12.1%; ours at `REST_MIX 14%` runs 13.9 / 31 / 18.5%. Ours is flatter (hard cap 37 vs the reference's 77 peaks) because a solid text colour has no antialiasing falloff and the reference is an H.264 encode — that residual is not worth chasing.
- **Layout.** The band needed `-mb-[15vw]` so the field bleeds behind the name, and `PLANE_FILL 1`. Without both, a ~2:1 artwork in a ~3.6:1 band fits to height and the hands span barely half the width.

> **Two measurement traps I hit** — worth not repeating. Comparing crops of the reference (3600 px frame) against a 2× screenshot (2880 px) at the *same pixel dimensions* compares different CSS areas: it made the field look 5× too bright and the grid look twice as coarse as it was. Normalise both to the same CSS width first. Everything above is post-normalisation.
